# CareSync deployment preparation review

Reviewed on 6 October 2026, starting from commit `1bd8e15`. Results apply to the deployment preparation changes introduced after that commit. Hosting deployment was not performed as part of this review.

## Result

The review found defects and hosting blockers, which were corrected. All 17 backend check files, the frontend production build, and both browser check suites passed after the application changes. A separate production configuration check confirmed that the compiled website uses the hosted API URL.

This is evidence of the checked behavior, not a guarantee that no errors remain. Real Atlas storage, Google authorization, email delivery and installed mobile behavior must be verified after the user configures the hosting accounts. Follow the [deployment guide](free-hosting-guide.md).

## Scope

- Backend configuration/startup, authentication, account and OTP flows, role restrictions, appointment and queue workflows, scheduling/concurrency/recovery, notifications, reports and audit records.
- Consultation uploads/downloads, document replacement/archiving and original version access, including local and new GridFS storage paths.
- Frontend API configuration, session restoration, upload field ordering, dashboards, forms, dialogs, navigation and responsive layouts.
- The separate mobile repository's API base URL setting, request timeout, authentication error handling and Android internet permission were inspected read-only. Its full Flutter suite and a hosted APK were not run in this review.
- The existing specification PDF and historical testing evidence were not regenerated. This document records the additional deployment review.

## Findings corrected

| Finding | Change | Verification |
| --- | --- | --- |
| The frontend depended on the local Vite proxy, which does not exist on the deployed static website. | Added the public build-time `VITE_API_BASE_URL` setting and reject unexpected successful responses such as an HTML fallback. | Production build and an in-memory build using a sample hosted API URL. |
| Local uploaded files would disappear on a free host restart/redeploy. | Added MongoDB GridFS storage, protected downloads and current/historical version support; production defaults to GridFS. | Isolated streaming storage checks, protected access, replacement/archive/download checks. Actual persistence needs a hosted restart test. |
| Existing database records can still reference local upload bytes. | Added a migration with a read-only default inventory, containment checks, explicit offline apply mode, resumable copied files and preservation of local originals. | Snapshot/path checks and syntax check. Migration was not executed against the user's database. |
| SMTP cannot deliver email from Render Free because its SMTP ports are blocked. | Added Gmail HTTPS API transport with OAuth refresh, concurrent token refresh sharing, safe MIME encoding and provider error handling; retained SMTP for local use. | Mocked token/send responses, invalid recipients, scope/auth failures, rate limiting and cache invalidation. No Google request or real message was sent by these checks. |
| A temporary database failure was reported as an invalid login token; failed frontend restoration erased the login. | Pass database failures to the server error handler; retain valid stored tokens on temporary failures and show a retry option. Invalid credentials still clear the session. | Deployment route checks and desktop/mobile browser restoration checks for 503 and 401 responses. |
| Hosts using UTC could interpret clinic hours differently from the local Philippine clock. | Default and validate the backend timezone as `Asia/Manila`; set it in the hosting configuration. | Manila opening/closing boundary checks. |
| Upload fields were appended after the file, so local disk routing could miss the selected category. | Submit category/title/version before the multipart file. | Browser workflows and existing upload checks. |
| Failed file attachment could leave an unused upload; blindly deleting it could remove a file after a committed write with a failed acknowledgement. | Check current/archived/version references before removing unattached files. Storage-stream and multipart failures also clean up their temporary files. | Stale version, write/stream failure, oversize/multiple files and committed-write acknowledgement cases. |
| Malformed JSON and upload limits could return an incorrect 500. Raw internal failures could expose details in production. | Honor parser statuses; map oversize files to 413 and other multipart errors to 400; mask unexpected internal errors while keeping explicit actionable application errors. | HTTP error status and production response checks. |
| Production browsers had no explicit allowed-origin configuration, and the health endpoint reported success without database connectivity. | Exact CORS origin allowlist, native-client support, proxy-hop setting and database-aware health response. | Allowed/denied/preflight origins, client IP and healthy/disconnected status checks. |
| Login attempts were not throttled; invalid audit pagination could reach MongoDB. | Apply the existing account request limiter to login and validate pagination bounds. | Login threshold/client-IP and invalid pagination checks. |
| User uniqueness indexes were not explicitly awaited before accepting requests. | Await User model initialization with the other startup indexes. | Code/startup review and syntax checks; existing Atlas indexes still need to initialize successfully on deployment. |
| Queue diagnostic logs included patient names. | Log only the ticket number. | Source review. |

### Repeat the backend checks

From the repository root with dependencies installed:

```powershell
$checkFiles = Get-ChildItem backend/tests/*.check.js | Sort-Object Name
foreach ($checkFile in $checkFiles) {
    node $checkFile.FullName
    if ($LASTEXITCODE -ne 0) { throw "Failed: $($checkFile.Name)" }
}
npm.cmd --prefix frontend run build
```

Browser checks need Chrome and a running frontend preview. The focused check uses Node's browser-debugging client and is documented in the README. The full `docs/ui-smoke.mjs` check additionally accepts a Puppeteer module path as its first argument. Both use the built frontend and isolated API responses.

## Remaining checks before the demonstration

1. Back up existing data and upload bytes; migrate local files only with all API writers stopped. Inventory is read-only unless explicit apply flags are provided.
2. Configure Atlas access, Google OAuth and host secrets; run the outstanding backend dependency advisory check.
3. Verify real signup/password codes and appointment notifications. Google Testing refresh tokens expire after seven days with Gmail scopes; resolve the appropriate publishing configuration for longer use.
4. Verify real booking, staff assignment/check-in, doctor completion and queue updates across all roles.
5. Upload and replace a sample document, download both versions, restart/redeploy the backend, and download again. Verify another patient's access is denied.
6. Build/install the mobile app with the Render API URL and verify shared records across web/mobile. Wake `/health` before testing an idle free backend.

The proposed configuration uses one API process. Some background notifications and limits are process-local; durable notification retries are not implemented. Render Free sleeps after inactivity, and its wake-up can exceed the mobile app's current 20-second timeout. Atlas Free storage is limited, and retained file versions consume quota. These constraints are recorded in the deployment guide and are relevant to the demonstration.

No production deployment, real reset, database migration, account creation or real email send was performed during this review.
